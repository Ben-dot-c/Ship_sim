=== Folder Structure Session (2026-08-05) ===

Q: Why separate .cpp from .h files? What's the benefit and cost?
A: Code clarity and modularity.

Q: Should build artifacts live in src/ or somewhere separate? What problems might mixed locations cause?
A: Mixed locations could cause errors, but separate locations make file path handling easier.

Q: One .cpp/.h pair per class, or grouped together? What tradeoffs matter?
A: One pair per class — easier to edit each part independently. Possible downside: compile time / file count.

Q: Where should main() live?
A: In its own file, thin, like Python's if __name__ == "__main__" pattern — orchestration only.

Q: Create empty placeholder files now, or wait until the classes are designed?
A: Create them now — can't reference/call something that doesn't exist yet.

=== Save Viewer: Load Class Design Session (2026-08-07) ===

Q: Should the Stat pair's string label (e.g. "Strength") be saved to the JSON file every time, or can it be skipped?
A: It's a fixed constant tied to the stat category and never changes — skip saving it, reconstruct it on load instead. The vector will later hold multiple entries per stat (base value + item bonuses), not one entry per crew member.

Q: Should Load own its own Stat instances directly (mirroring Save)?
A: No — a separate CharacterSheet class will own the real Stat instances for a character. Load's job shrinks to reading the file and handing back raw values; this also sidesteps a member-initialization-order problem (Stat objects need a value before they're constructed, but the file isn't read until the constructor body runs).

Q: Should the Stat constructor keep a default int value, to cover missing save data?
A: No default — "default to 1 only if the save data is missing" is a runtime JSON-lookup decision (nlohmann's `.value(key, 1)`), not something a C++ default parameter can express (a default parameter only knows whether an argument was omitted, not what's in a file).

Q: What shape should Load's raw output take — array, tuple, or named struct?
A: Named struct (`stat_holder`, 5 ints) — there are always exactly 5 stats, so there's no need for index-based iteration at this level; direct named field access (`.str`) avoids index-order mistakes that a tuple or array would risk.

Q: Should Load's constructor read the file, or should load_game() re-read it on every call?
A: Constructor reads once, into a member — avoids re-parsing the JSON on every call, which matters once looping over multiple characters later.

Q: Cache the extracted stat_holder, or the raw parsed json, as Load's member?
A: Raw parsed json (`data`) — keeps Load ready to extract multiple characters from the same parse later, without re-reading the file each time.

Q: One "character sheet" class holding data for all 8 party members, or one sheet per character plus a separate container?
A: Separate — CharacterSheet stays scoped to one character; a future Party class holds up to 8 CharacterSheets.

Q: What's the difference between a class and a struct in C++?
A: Almost nothing — the only difference is default member access (struct defaults to public, class defaults to private). "Member" applies equally to both; it's not struct-specific.
